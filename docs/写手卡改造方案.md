# 写手卡 + 角色池改造设计方案

> 在 `MoonChatBook` 副本里实施。验收通过后回替主项目 QQbot。
> 日期：2026-10-03

---

## 一、核心认知（先纠正一处理解偏差）

**现有 4 个 bot 就是 4 个写手，不需要拆分。**

最初的误解是「一个 bot = 一个角色，要拆成写手 + 角色两份」。实际是：

> **bot 本身就是写手**（创作者）。角色是写手笔下的人物，存在于**角色池**里。

所以这次改造的实质是三件事：

| # | 改造 | 说明 |
|---|---|---|
| 1 | **改名 + 改语义** | 「角色卡」→「写手卡」；`persona.md` 从「角色人格」变成「写手设定」（创作风格 / 叙事口吻） |
| 2 | **新增角色池** | 全局共享的角色库，写手从里面挑角色来写 |
| 3 | **记忆分层确认** | `memory/<botId>/` **保持现状**，它本来就是写手记忆；只是里面要区分「剧情线」与「写手设定」 |

## 二、数据结构

### 2.1 写手（就是现在的 bot）

```js
config.bots[] = {
  id: 'BOT1',
  name: '归云',                    // 写手名
  kind: 'writer',                  // ★ 新增，恒为 'writer'（显式标记，便于将来扩展）
  modelId: 'Agnes',
  avatar: '/avatars/xxx.webp',     // 写手的形象（不是角色的）
  activeCharacterIds: [],          // ★ 新增：这个写手当前在写的角色（有序）
  enabled / sandbox / appId ...    // 全部保留不动
}
```

### 2.2 角色池（全局共享，新增顶层字段）

```js
config.characters = [
  {
    id: 'CHR1a2b3',
    name: '小鱼',
    // 角色设定（原 persona.md 的内容结构）
    persona: '13岁男孩，被原生家庭虐待后遭「我」收养……',
    traits: '胆小、沉默寡言、警惕心强',
    // 结构化扩展（可选，从 WORLDS.md 迁移时填充）
    age: '13',
    appearance: '身材偏矮，微微发胖……',
    background: '父亲酗酒家暴……',
    // 归属与来源
    tags: ['主要角色'],
    source: 'BOT2/WORLDS.md',      // ★ 迁移来源，便于追溯
    avatar: '',
    ts: 1790000000000,
    // 版本档（用户决策 2：写手改角色卡要可回滚）
    history: [
      { ts: 1790000000000, by: 'user', persona: '…', traits: '…' },
      { ts: 1790000100000, by: 'BOT2', persona: '…', traits: '…' },
    ],
  },
]
```

### 2.3 记忆目录（**保持现状，不新增层级**）

```
memory/
  BOT1/                    ← 写手 BOT1 的记忆（原本就是，不动）
    persona.md             ← 改语义：写手设定（创作风格）
    plot.md                ← 剧情线（tier1~2）
    events.jsonl           ← 经历事件
    _meta.json             ← 层级配置
  global/                  ← 全局设定（已有）
  admin/                   ← 管理员记忆（已有）
```

★ **不建 `memory/writer/` 目录**。`memory/<botId>/` 就是写手记忆，
建新目录只会引入迁移成本而没有收益。

## 三、角色池的存储位置

**`config.json` 的顶层 `characters` 数组**（全局共享，用户已确认）。

⚠️ 风险提示：`getConfig()` 每次请求读盘，角色池大了（比如 100 个角色 × 每个 2KB 设定
= 200KB），`config.json` 会显著变大。但相比「单独存 `characters.json`」的方案，
放在 `config.json` 里能享受现有的**整份覆盖 + 基线探针 + 原子写入**机制，一致性更有保障。
**暂定放 `config.json`**，若后续实测变慢再拆文件。

## 四、写手行为逻辑（用户决策 1：叙述/对白自主混合）

写手的 system prompt 需要组装三部分：

```
【写手设定】      ← 来自 memory/<writerId>/persona.md
   你是一位写手，擅长……

【剧情线】        ← 来自 memory/<writerId>/plot.md + events（经历）
   当前主线：……

【角色池·可用角色】 ← 来自 config.characters（只注入 activeCharacterIds 里的）
   - 小鱼：13岁男孩，胆小沉默……（与「我」的关系：刚被收养）
   - 苏然：14岁，校霸……
```

写手自主决定：

- **叙述**（推进剧情）：输出小说体文字，角色在文中说话
- **对白**（扮演角色）：以某个角色的第一人称直接对话
- **建档**：剧情需要新人物时，写手可提议把新角色落进角色池

### 与现有机制的兼容

| 现有机制 | 处理 |
|---|---|
| 长文模式 / 分段续写 | **保留**，小说的长段落正需要它 |
| 进度条 SSE `progress` | **保留**，写长文时正好用 |
| 流式 SSE | **保留**，不变 |
| 长度自主权 | **保留**，但语义变为「这一章写多长」 |
| 角色单独聊（决策 3） | **保留**：选一个角色单独开对话，走原路径 |

## 五、角色卡改写 + 回滚（用户决策 2）

写手改写角色卡时：

1. 写手通过工具 `propose_character_edit` 提交修改建议（**复用现有 pending 待确认机制**）
2. 用户确认后写入 `config.characters[]`，**写入前把当前版本 push 进 `history[]`**
3. UI 显示「谁改的」（`by: 'BOT2'` 或 `'user'`）+ 「回滚到此版本」按钮

★ 与现有的 `persona_core.json` 的 `manual: true` 抑制重蒸馏机制**不冲突** ——
那是写手自己人格核心的机制，这是角色设定的机制，两套独立。

## 六、迁移方案（自动升级）

启动时检测：`config.characters` 不存在 → 执行迁移。

```
对每个 bot：
  1. 加 kind: 'writer'
  2. 加 activeCharacterIds: []
  3. 读 memory/<botId>/persona.md：
     - 若内容非空且不是空模板（>150 字节）
       → 创建一条角色（source: '<botId>/persona.md'），加入全局角色池
       → 把该 bot 的 activeCharacterIds 设为 [该角色 id]
       → ★ persona.md 本身**不动**（用户可自行决定是否改成写手设定）
  4. plot.md / WORLDS.md / 剧情记录.md → 保持原位（它们已是写手记忆的一部分）
```

**实测数据预判：**

| bot | persona.md | 迁移结果 |
|---|---|---|
| BOT1 归云 | 806B（真内容：「银」） | 建角色「银」，activeCharacterIds=[银] |
| BOT2 洛天 | 106B（空模板） | **不建角色**（是空模板）；角色从 WORLDS.md 手动迁移 |
| BOT3 昭 | 106B（空模板） | 不建角色 |
| BOT4 测试账号 | 106B（空模板） | 不建角色 |

★ 空模板判定：内容去空白后 ≤150 字节，或与 `DEFAULTS.persona` 高度相似。
**不能只看长度** —— 要跟 `DEFAULTS` 比对，否则用户手写的短人格会被误判为空。

## 九、待决问题（不阻塞开工，但需要你留意）

1. **BOT2 的 WORLDS.md 里的角色归属**：那 143KB 定义了「我 / 小鱼 / 苏然」等。
   剧情归 BOT2 写手、角色进全局库，那这些角色算谁的？
   暂定：角色池条目带 `source: 'BOT2/WORLDS.md'` 追溯来源，归属问题延后。
2. **`bot.moments`（精彩时刻）的归属**：现在是写手的，改成「某个角色的精彩时刻」？
   暂定：保留在写手侧（它是写手提炼的剧情高光）。
3. **写手是否需要连 QQ**：现在 bot 有 `enabled` / `sandbox` 是给 QQ 用的。
   写手若也对外发消息，那它就是「会聊天的写手」。**暂定保留 QQ 能力不动。**
