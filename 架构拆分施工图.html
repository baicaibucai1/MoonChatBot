02三个病灶拆分前实测 · 现已修复

不是「代码风格不好」这种虚的，是三个会实际咬人的具体问题。
路由与业务混装 703 行

43 条路由写成一条线性 if 链，每条路由的判定、参数提取、业务逻辑、响应拼装全揉在一起。想给某条路由加测试，得先把整个 handleApi 跑起来（而它依赖 memory、app、fs 全局）。

单函数超长 250 行

adminToolSchemas 250 行、runAdminTool 190 行、chatWithBot 161 行。三个函数加起来 601 行，都超过任何编辑器的可读窗口，改动全靠上下翻找。

字符类复制粘贴 34 处

/^[\w\u4e00-\u9fa5-]{1,64}$/ 这个 ID 校验规则在文件里出现 34 次。ID_RE 和 ADMIN_ID_RE 是两份内容完全相同的常量 —— 改校验规则必须改 34 个地方，漏一个就是入口不一致。

顺带发现（批 0 基线已记录）： if (p === '/api/state') 写在 1286 行，没有方法校验 —— POST /api/state、DELETE /api/state 都会走进同一分支并返回 200。 另外 POST /api/bots/:id/chat（1738 行）没有前置实体校验，带任意 id 请求就能在 memory/ 下凭空造出目录和会话记录。这两个都在批 2 一并修。
